# План та результати тестування — ЛР №6

## Підготовка та інструменти

Вихідні дані — інтегрований моноліт із ЛР №5 (`README.md`, `docs/integration.md`),
перелік FR-01—FR-09 і NFR-01—NFR-07 з ЛР №2. Тести запускаються в ізольованій
тестовій БД через `django.test`; `coverage.py 7.17.0` використано лише для
вимірювання покриття. Системний прогін використовує стандартну бібліотеку
Python, HTTP до справжнього локального Django runserver та `/proc` у Linux.
Selenium/Postman тут не потрібні: публічного JSON API немає, браузерні
випробування в трьох рушіях не заявляються без фактичного запуску.

## Рівні, сценарії, очікувані результати

| Рівень | Перевірки | Очікування |
| --- | --- | --- |
| Юніт | `test_unit_logic.py`: генератор 8 символів, алфавіт, HTTP/HTTPS, некоректні схеми, наддовгий URL; `test_links.py`: колізії коду, повтори з обмеженням, фільтр власника | Коректні дані прийнято; помилки відхилено, код унікальний |
| Компонентний | `test_components.py`: view → форма/сервіс, view → сервіс → ORM, права власника, обробка помилки БД; `test_links.py`: CSRF, HTTP 302/404/405, Auth | Належні HTTP-статуси, URL, права й лічильник |
| Системний | `test_system.py`, `test_integration.py`: вхід/вихід або реєстрація → створення → список → публічний перехід → статистика → видалення, Admin; `scripts/system_probe.py`: реальний HTTP, паралельне навантаження, RSS, перезапуск | Користувацькі сценарії працюють, час <2 с локально, дані після перезапуску є |

`TestCase` не запускає графічний браузер, але проходить Django middleware,
маршрути, форми, шаблони, Auth, сервіси і тестову БД. На системному рівні
окремо застосовано мережевий HTTP-прогін для поведінки реального процесу.

## Результати (локальний прогін)

- `manage.py test`: **29 тестів, 29 успішних**, `manage.py check`: без проблем.
- `coverage run --source=links -m manage test` і `coverage report --include=...`:
  **110 виконаних із 110 операторів = 100%** для `links/forms.py`,
  `links/models.py`, `links/services.py`, `links/views.py`, `links/admin.py`.
  Це *statement coverage*, не branch coverage; `config/`, скрипти та сторонні
  бібліотеки в цьому показнику не враховано.
- `scripts/system_probe.py`: 20 одночасних автентифікованих сесій, 3 раунди
  `/links/`, `/links/new/`, `/<code>/` = **180 запитів, 0 помилок**;
  медіана **0,070 с**, p95 **0,753 с**, максимум **1,237 с**. Отже, локальний
  результат для NFR-01 (<2 с) позитивний, але runserver не є production.
- Linux `VmRSS` процесу runserver: до навантаження **55 052 KiB**, спостережений
  пік **67 244 KiB**, приріст **12 192 KiB**. Це лише серверний процес в одному
  прогоні (не повна пам'ять машини); для пам'яті в NFR немає числового порога,
  отже «відповідає нормі» за цим показником стверджувати не можна.
- NFR-07 локально: запис у тимчасовій SQLite створено до старту сервера;
  після завершення і нового запуску процесу публічний URL повернув 302 та
  збережену адресу. Постійний том хостингу цим не перевіряється.

## Знайдені проблеми, вплив, виправлення

Під час аналізу покриття виявлено **дубльовану перевірку довжини URL** в
`LinkService.create`: штатний `URLValidator` Django вже відхиляє URL понад
2048 символів до виконання другого `if`. Вплив — надлишковий код і
недосяжна гілка, не виявлений користувацький збій. Видалено зайву перевірку
та імпорт, негативний тест залишено; повторний запуск — 29/29 успішно.
Функціональних дефектів у перевірених сценаріях не знайдено; це **не** гарантія
відсутності інших дефектів і не заміна production-випробувань.

## Рекомендації і відкриті роботи

1. Провести реальні ручні сценарії реєстрація → створення → перехід → видалення
   окремо в Chrome, Firefox та Edge, включно з мобільною шириною (NFR-04).
2. Розгорнути через WSGI/TLS-проксі, перевірити HTTPS-редирект, cookies,
   заголовки безпеки, `check --deploy`; після цього повторити навантаження
   без тестових записів у production-БД. Розглянути PostgreSQL для більшого
   паралельного навантаження: SQLite має обмеження на одночасні записи.
3. На постійному диску перевірити перезапуск і відновлення з резервної копії;
   встановити цільовий поріг пам'яті для реальної інфраструктури.
4. Подальше розширення (не входить до FR-01—FR-09): обмеження частоти
   створення посилань, докладна статистика та експорт за окремим запитом.

Роботу виконано індивідуально: обговорення в команді не проводилося.
